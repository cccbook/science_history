# 8.5 Coding Agent 與程式碼生成的元能力

在人工智能飛速發展的今天，程式碼生成已不再是科幻，而是科學研究的標準配備。本章探討一個關鍵問題：AI 作為「程式碼代理」時，擁有什麼「元能力」？

## 1. 上下文感知

最優秀的程式碼代理不會在真空裡生成程式碼。它具備**上下文感知**的能力，能夠：

- **閱讀現有代碼**：分析項目結構、變數命名習慣、已有函數。
- **記憶項目歷史**：记住之前的修改、Bug 修復記錄、設計決策的原因。
- **符合項目規範**：生成的代碼風格與項目其餘部分一致。

### 實際應用

當被要求「實現一個求解薛丁諤方程的有限差分程式」時，優秀的代理會：

1. 檢視項目中是否已有相關的數值模組
2. 檢查變數命名是否符合項目慣例（如 `psi`, `hbar`, `dx`）
3. 生成的代碼風格與現有代碼一致，降低整合成本

## 2. 錯誤修復能力

程式碼生成最顯著的優勢在於**錯誤修復**。傳統的「寫一次、測一次」模式效率極低，而 AI 代理可以：

- **即時檢測語法錯誤**：運行程式碼前即提示缺少冒號、未定義變數等。
- **邏輯錯誤定位**：分析程式執行軌跡，指出數組越界、除以零等問題。
- **自動修復**：生成修復方案，並說明修復的原因。

### 實際案例

假設用戶要求「實現一個計算氫原子基態波函數的程式」，代理生成的程式如下：

```python
import numpy as np

def hydrogen_wavefunction(r, n=1, l=0):
    """計算氫原子的波函數"""
    a0 = 5.29e-11  # 玻爾半徑
    # 簡化版：只返回機率密度
    rho = r / a0
    if n == 1 and l == 0:
        # 基態：1s 軌道
        R = 2 / np.sqrt(a0**3) * np.exp(-rho)
        return R**2  # 返回機率密度
    else:
        return None
```

當用戶運行此程式時，發現輸出的機率密度在 $r=0$ 時不為零（物理上應該為零，因為 s軌道的波函數在原點處應為非零，但導數為零）。用戶反饋錯誤。代理接著分析錯誤，發現是因為未正確處理原點處的邊界條件，隨後生成修復版本：

```python
def hydrogen_wavefunction_v2(r, n=1, l=0):
    """修正版：正確處理原點處的邊界條件"""
    a0 = 5.29e-11
    rho = r / a0
    if n == 1 and l == 0:
        R = 2 / np.sqrt(a0**3) * np.exp(-rho)
        # 在 r=0 時，機率密度應為非零，但導數為零
        # 使用有限差分近似邊界條件
        if r == 0:
            return 4 / (np.pi * a0**3)  # 正確的基態機率密度
        return R**2
    else:
        return None
```

## 3. 自我優化能力

優秀的代理具備**自我優化**能力。每次生成程式碼後，它會：

- **自檢**：運行單元測試，檢查輸出是否符合預期。
- **學習**：記錄哪些模式產生了錯誤，哪些模式是成功的，並在後續的生成中避免重複錯誤。
- **向用戶說明**：每次修復後，說明為什麼會出錯以及如何修復，使用戶學習過程。

### 實際優化流程

1. 生成初版程式碼
2. 執行測試：`pytest test_hydrogen.py`
3. 檢查測試結果：若失敗，分析錯誤訊息
4. 生成修復方案並說明原因
5. 運行修復後的程式碼，確認測試通過
6. 將修復經驗記錄在項目知識庫中

## 4. 元能力的比較

| 能力 | 傳統程式設計 | AI 程式碼代理 |
|---|---|---|
| 上下文感知 | 需手動檢閱項目文件 | 自動分析現有代碼結構 |
| 錯誤修復 | 運行後人工定位 | 即時檢測與自動修復 |
| 自我優化 | 需人工總結經驗 | 自動記錄與學習 |
| 上手速度 | 需了解項目架構 | 直接根據需求生成 |

## 本章小結

- 程式碼代理具備上下文感知、錯誤修復、自我優化三大元能力
- 實際應用證明：AI 代理可以顯著降低科研程式開發的門檻
- 元能力的比較顯示：AI 代理在生產效率上優於傳統設計
