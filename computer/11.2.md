# 11.2 HTTP、HTML 與 URL：三位一體的世界網頁

## 從理論到實作：萬維網的誕生

1990年，蒂姆·伯納斯-李在 CERN 的 NeXT 電腦上，實作了世界上第一個網頁瀏覽器與伺服器。這標誌著萬維網（World Wide Web，W3）從理論走向實際應用。三大核心技術——URL、HTTP、HTML——開始在真實的網路環境中運作，讓使用者得以體驗「跨設備、跨平台」的資訊瀏覽方式。

在那個年代，若要在兩台電腦間傳輸文件，需要經由 FTP（檔案傳輸協定）等專用協議，且必須瞭解對方的 exact 檔案路徑。而有了 URL、HTTP、HTML 後，使用者只需要在瀏覽器中輸入網址，即可透過 HTTP 取得 HTML 文件，瀏覽器再將其渲染為可視的網頁。這種簡單性，徹底改變了人類互動資訊的方式。

## URL：資源的唯一識別碼

URL 的設計哲學在於「唯一性」與「可擴充性」。每個資源在互聯網上擁有唯一的 URL，這意味著無論資源位於何伺服器、以何種協議傳輸，其識別碼永遠不變。

URL 的結構極其直觀：`scheme://host/path?query#fragment`。我們可以解構一個典型的 URL 以了解其組成：

- **scheme**：協議類型，如 `http`、`https`、`ftp`、`mailto` 等。它告訴客戶端如何連線到伺服器。
- **host**：主機名稱或 IP 位址，代表資源所在的伺服器。如 `www.example.com` 或 `192.168.1.1`。
- **path**：資源在伺服器上的路徑。如 `/search?q=article`，指向伺服器上 `search` 目錄下的 `article` 檔案。
- **query**：查詢字串，使用 `?` 開頭，由鍵值對 `key=value` 以 `&` 分隔。如 `?sort=desc&limit=10`，用於傳遞搜尋參數。
- **fragment**：錨點，使用 `#` 開頭，指向資源內部的特定位置。如 `#section-3`，瀏覽器會自動捲動至對應區塊。

URL 的靈活性體現在其能夠跨協議運作：同樣的主機名稱，可以透過 `http` 取得網頁、透過 `ftp` 下載檔案、透過 `mailto` 啟動郵件客戶端。這種抽象，讓互聯網的擴充無需重新定義位址結構，僅需新增對應的 scheme 即可。

## HTML：內容的語意標記

HTML 的發展經歷了多個版本，從最初的簡單標籤，到如今支援豐富媒體與互動的 HTML5。然而，其核心哲學始終未變：標記資源的語意結構，而非描述視覺呈現。

HTML 的標籤分為幾大類：

- **文本與段落**：`<h1>` 到 `<h6>`（標題）、`<p>`（段落）、`<li>`（項目列表）
- **超連結**：`<a>`（銜接至其他資源），其 `href` 屬性即為 URL
- **圖片與媒體**：`<img>`（插入圖片，`src` 屬性為圖片 URL）、`<video>`、`<audio>`（多媒體元素）
- **表單**：`<form>`（收集使用者輸入），結合 `<input>`、`<select>` 等控制項，透過 HTTP `POST` 方法將資料提交至伺服器

HTML5 的出現，進一步豐富了標籤庫，新增了 `<canvas>`（繪圖）、`<svg>`（向量圖形）、`<section>`、`<article>` 等語意化標籤。這些標籤不僅提升了搜尋引擎的收錄效率，也改善了輔助技術（如スクリーンリーダー）對網頁內容的解讀。

更有趣的是，HTML 的發展始終與瀏覽器廠商的市場博弈緊密相連。1990年代的「瀏覽器大戰」（Netscape Navigator 對微軟 Internet Explorer）導致了許多專有擴充標籤的產生，如 `<marquee>`（滾動文字）與 `<blink>`（閃爍文字）。然而，萬維網聯盟（W3C）與 WHATWG（網頁標準協會）致力於標準化，最終遏制了專有擴充，確保了 HTML 的跨平台相容性。

## HTTP：協議的演進

HTTP 的版本歷程，見證了互聯網規模的擴大與需求的演變：

- **HTTP/0.9**：極簡版本，僅支援 `GET` 一種請求方法，回應純文字的 HTML 文件。沒有請求頭、回應頭，極度精簡。
- **HTTP/1.0**：引入了請求頭與回應頭，支援多種請求方法、內容協商（如支援圖片格式的協商）與狀態碼（如 200 OK、404 Not Found）。
- **HTTP/1.1**：成為長達十多年的主流版本。它引入了連線重用（同一個 TCP 連接可發送多個請求）、內容長度與緩衝機制、以及持久連接。雖然效能優越，但因頭部搭載大量冗餘資訊（如冗餘的請求頭），在高延遲網路下表現有限。
- **HTTP/2**：基於 Google 的 SPDY 計畫，引入了二進位封展、多路複用（同一連接上並行發送多個請求與回應）、header 壓縮與伺服器推送。這極大降低了延遲，提升了頁面載入速度。
- **HTTP/3**：最新版本，不再基於 TCP 協議，而改用 **QUIC** 協議（基於 UDP）。它解決了 TCP 的頭阻塞問題，實現了更快的連線建立與更穩定的傳輸品質。

HTTP 的演進，始終圍繞於「效能、安全性與簡潔性」三者之間的平衡。每一個版本都在吸取前人經驗，試圖在維持向後相容的同時，滿足日益複雜的網頁應用需求。

## 三者的協作流程

為了讓讀者更直觀地了解三者如何協同工作，我們以一個典型場景為例：使用者在瀏覽器中輸入 `https://www.example.com/search?q=hello` 並按下 Enter。

1. **URL 解析**：瀏覽器解析 URL，識別 scheme 為 `https`，主機為 `www.example.com`，path 為 `/search`，query 為 `q=hello`。
2. **DNS 解析**：瀏覽器透過 DNS 將主機名稱 `www.example.com` 解析為 IP 位址（假設為 `93.184.216.34`）。
3. **連線建立**：瀏覽器透過 TLS/SSL 協商加密連線，建立與伺服器的 TCP（或 QUIC）連結。
4. **HTTP 請求**：瀏覽器發送 HTTP GET 請求，首部包含 `Host: www.example.com`、`User-Agent`、`Accept: text/html` 等資訊；查詢字串 `q=hello` 附加在 URL 後。
5. **伺服器處理**：伺服器接收請求，解析 `q=hello`，檢索資料庫中關鍵字為 'hello' 的搜尋結果，組成 HTML 文件。
6. **HTML 傳輸**：伺服器以 HTTP 回應回覆，狀態碼 `200 OK`，首部包含 `Content-Type: text/html`，主體為組好的 HTML 碼。
7. **頁面渲染**：瀏覽器接收 HTML，解析標籤結構，載入圖片、CSS（雖然本例未包含，但實務中往往連帶載入），執行 JavaScript（若有），最終呈現可視的搜尋結果頁面。

這個流程，雖然步驟繁瑣，但對使用者而言僅耗數秒。更神奇的是，這套機制能夠支援全球數以億計的同時在線使用者，這正是 URL、HTTP、HTML 三大基石設計之巧妙之處。

## 本章小結

- URL、HTTP、HTML 三大基石共同構成了萬維網的完整堆疊：URL 定位資源、HTTP 傳輸資源、HTML 解讀資源內容
- URL 的結構極其直觀與靈活，支援跨協議、跨主機的資源識別
- HTML 的標籤語意化設計，將內容與呈現分離，利搜尋引擎、輔助技術與跨平台瀏覽
- HTTP 的演進歷程（0.9→1.1→2→3），見證了互聯網效能需求的指數成長，不斷優化傳輸效能與安全性
- 三者的協作流程，將使用者的輸入轉化為實際的網頁內容，形成了我們日常瀏覽網路的基本流程

## 想一想

1. URL 的設計極度依賴 DNS 將域名解析為 IP 位址。若 DNS 發生大規模故障或被污染，用戶是否還能直接透過 IP 位址存取網站？這中間的門檻與風險是什麼？

2. HTML 的語意化標籤（如 `<article>、<section>`）在提升搜尋引擎優化（SEO）與輔助技術（屏幕閱讀器）方面扮演了關鍵角色。若 HTML 完全關注視覺呈現（如早期的 `<font>、<center>`），現代的搜尋引擎與無障礙網頁將面臨何種挑戰？

3. HTTP/3 基於 QUIC 協議（UDP）與 HTTP/2（TCP）相比，最大的優勢在於解決了頭阻塞問題。在今天的邊緣計算與實時通訊場景，這項技術優勢是否足以彌補 UDP 本身缺乏可靠性、順序性的缺點？還是需要額外的應用層機制來彌補？
