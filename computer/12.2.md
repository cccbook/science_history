# 12.2 SQL 的誕生與 ACID 事務特性

## From Declarative Query to Transactional Backbone

在 12.1 節中，我們探討了關聯模型與關聯代數的理論基石。這一節，我們將目光聚焦於將這些理念轉化為實際工具的 **SQL**（Structured Query Language，結構化查詢語言）。SQL 不僅僅是一門查詢語言，更是一套支撐企業級資料庫系統的事務處理規範。

## SQL 的早期演進

1970 年代末，ibm 的項目 **System R** 開始實作關聯模型的實作原型。研究人員發現，單純的關聯代數運算，雖然數學優美，卻難以直接應對企業級應用中常見的複雜交易需求。為了解決這一問題，他們設計了一門名為 **SEQUEL** 的語言（後因商標問題，簡化為 SQL）。

SQL 的設計哲學極其貫徹：「盡可能讓使用者聲明『我想要什麼』，而非『該如何去獲取』」。這與當時主流的遊標遊標遊標（Cursor-based）程式設計形成鮮明對比。在遊標模式下，程式員必須顯式地開啟遊標、逐行撈取資料、手動關閉遊標，易錯且效能低落。而 SQL 的聲明式語法，讓使用者只需描述「我想要所有姓氏開頭為「張」的顧客資訊」，資料庫引擎自行負責最優的執行計劃與資源調配。

1986年，SQL 成為 ANSI 標準；1992年，演進為 ISO/IEC 9075 標準。這標誌著 SQL 不再是 ibm 的內部實驗，而是一門開放、跨平台的資料庫語言。自此，SQL 成為了資訊產業的通用語言，支撐著關聯式資料庫的絲絲繆繆。

## ACID：事務處理的鐵律

在商業應用中，資料的一致性與可靠性至關重要。為了確保資料庫在面對系統故障、電源中斷或使用者錯誤時，依然能維護好資料的完整性，SQL 標準定義了 **ACID** 四大屬性：

### 1. 原子性（Atomicity）

原子性要求於一個事務中，所有的操作要麼全部成功，要麼全部失敗。不存在「部分成功」的情況。

舉例來說，轉帳交易包含兩個動作：從帳戶 A 扣除 1000 元，將 1000 元加入帳戶 B。若在轉帳過程中，系統發生 crash（如斷電），原子性機制確保：若扣除成功卻未能成功加入帳戶 B，整個事務會被「回滾」，帳戶 A 的錢會自動歸還，帳戶 B 不會收到任何款項。這避免了資金帳目的不一致。

### 2. 一致性（Consistency）

一致性要求事務執行前後，資料庫必須維持預設的完整性約束。這包括主鍵唯一性、外鍵Referential Integrity（Referential Integrity，RI）、觸發器定義的業務規則等。

舉例來說，若有一個約束規定「客戶的信用額度必須大於 0」，則任何事務不得導致該約束被違規違背。若事務嘗試違背該約束，資料庫會予以拒絕，回滾至事務前的一致狀態。

### 3. 隔離性（Isolation）

隔離性要求並發執行的多個事務，不應相互干擾。每個事務應視為在獨立的環境中運行， intermediate（中間）狀態對其他事務應不可见。

舉例來說，若事務 A 正在更新帳戶餘額，事務 B 若同時讀取該餘額，應讀到的是事務 A 執行前的值，而非未完成的中間值。這透過 **鎖機制**（Locking）或 **多版本並行控制**（MVCC）等技術來實現。MVCC 在 PostgreSQL、MySQL (InnoDB) 中極為常見：它維護著資料的多個版本，讓讀取操作不需要等待寫入操作結束，極大提升了並發效能。

### 4. 持久性（Durability）

持久性要求一旦事務提交，其所作的修改應永久保存在資料庫中，即使發生系統 crash（如斷電、硬體損壞）亦然。為了實現持久性，資料庫通常會搭配「重做日誌」（Redo Log）與「備份」機制。寫入操作先記錄於重做日誌，事務提交後，日誌記錄才標記為永久；即便電源中斷，啟動時也能從日誌中復原未完成的事務。

## 事務隔離等級

為了在一致性與並發效能之間取得平衡，SQL 標準定義了四個事務隔離等級，依據「髒讀（Dirty Read）」、「不可重複讀（Non-repeatable Read）」與「幻讀（Phantom Read）」的發生頻率而定：

1. **Read Uncommitted（讀取未提交）**：最低級別。事務可以讀取到其他事務未提交的中間狀態。極易產生髒讀、不可重複讀與幻讀。
2. **Read Committed（讀取已提交）**：預設大多數資料庫（如 SQL Server、PostgreSQL）的預設級別。事務只能讀取到其他事務已提交的資料。消除髒讀，但仍可能出現不可重複讀與幻讀。
3. **Repeatable Read（可重複讀）**：大多數應用的常選級別。事務在整個執行期間，對同一筆資料反覆讀取，結果始終如一。消除不可重複讀，但可能仍出現幻讀。MySQL (InnoDB) 的預設級別。
3. **Serializable（可序列化）**：最高級別。事務的執行結果，等同於串行執行所有事務。完全消除髒讀、不可重複讀與幻讀，但效能代價最高，通常需要額外的鎖或 MVCC 優化。

選擇適當的隔離等級，是資料庫調優的關鍵一環。例如，金融交易系統極力求一致，會選擇 Serializable；而社交媒體的點讀系統，則可能選擇 Read Committed 以換取更高的並發吞吐。

## SQL 的永續影響力

SQL 的成功，在於它既滿足了理論純潔性（關聯代數），又兼顧了工程實務需求（效能、併發、容錯）。它不僅是一門查詢語言，更是一種「資料操作的集合運算子」。

至今，SQL 依然是資料庫領域的霸主。雖然 NoSQL（如 MongoDB、Redis、Cassandra）興起，試圖以非關聯模型解決大規模、高並發場景，但 SQL 的生態系統極其豐富：ORM 工具（如 Hibernate、Entity Framework）讓開發者能以物件導向思維操作關聯資料庫；資料倉儲工具（如 dbt、Looker）以 SQL 為核心進行轉換與分析；即使在 NewSQL 與雲端資料庫（如 Google Spanner、Amazon Aurora）中，SQL 的變體仍是核心交互介面。

更有趣的是，隨著 **NewSQL** 的登場，試圖在保持 SQL 熟悉度的同時，突破傳統關聯資料庫的擴展性瓶頸。Google 的 Spanner 結合了分散式系統的強一致性與傳統 SQL 的語法，讓全球分布的資料庫依然能夠使用熟悉的 SELECT、JOIN 等語句進行查詢。

## 本章小結

- SQL 源自關聯模型與關聯代數，聲明式語法讓使用者聚焦「想要什麼」而非「如何獲取」
- ACID 四大屬性（原子性、一致性、隔離性、持久性）是事務處理的鐵律，確保企業級資料庫的可靠性
- 四個事務隔離等級在一致性與並發效能間取得平衡，根據應用場景靈活選擇
- SQL 雖然面臨 NoSQL 的挑戰，卻憑藉其豐富的生態系統、熟悉度與標準化地位，繼續統治資料庫領域
- NewSQL 的登場，試圖在分散式架構中保持 SQL 的優勢，展現了 SQL 理論的持久生命力

## 想一想

1. ACID 四大屬性在微服務與分散式系統中極具挑戰。傳統的單體資料庫 ACID 很容易達成，但在跨服務事務（如 Saga 模式）中，如何在保持資料一致性的同時，避免系統過度鎖定導致的性能瓶頸？

2. SQL 的聲明式特性與傳統的遊標遊標遊標（Cursor-based）遊標程式設計形成鮮明對比。這種抽象層次的轉變，對於資料庫引擎的優化（如查詢重寫、費用估算）有何影響？現代的費用估算器是如何利用統計學與機器學習，預測最優執行計劃的？

3. 在大規模分散式環境下，傳統的 ACID 事務模型往往因為CAP定理而難以實現。新興的「弱一致性」資料庫（如 Cassandra、DynamoDB）是如何在犧牲堅一致性的換取可用性與分區容錯性的同時，提供可接受的讀寫體驗？這中間的權衡邏輯是什麼？
